# Activities, Phase 1: the core. Implementation plan

**Goal.** Build step 1 of the approved Activities design: the game's one clock (`gear::clock`); the rooms given minutes, not days; the tiers renamed Normal, Elite and Abyss everywhere; each character's day and week records and its story kept with the account; the page telling its room when the prologue is played; and the gates, kept by the rooms and shown to the player.

**Architecture.** All rules live in `gear`, which the server and the browser both run: the clock, the records (`activity.rs`, `story.rs`) and one gate function (`gate.rs`). The room (`crates/room`) holds the minute its host gives it, reads the day and week from `gear::clock`, knows what place it is (a social space, a patrol, a patrol's dungeon or another node) and its seas, and asks the gate before it gives a player their kept character.

The host (`server/keeping.ts`, `worker.ts`) asks the room through `room-wasm` whether the gate shuts. When it does, it lets the claim go untouched and closes the socket with code 4003 and the gate's reason. The page (`RoomConnection`, `Foot`, `flow.ts`, `game.ts`) does not rejoin a shut room. It takes the player back to their ship, and the veil shows the reason.

The prologue's end is a gear `Ask` with nothing in it. The gear message carries `prologue_done`, so the page asks again whenever the room's word says the character still lacks it. That covers the case where the ask lands before the kept character has been claimed.

**Tech stack.** Rust (workspace edition, serde, serde_json, libm only in `gear`), FlatBuffers (`crates/protocol/messages.fbs`, generated by `npm run schema`), wasm32 room door, TypeScript strict with `node --test`, Cloudflare Durable Objects and D1. The character is kept as JSON, so there is no migration.

**Spec path.** `bible/02-Systems/Activities.md` on `claude/activities`, step 1 of "How it is built". On disk: `/home/user/overlook-source/.claude/worktrees/activities/bible/02-Systems/Activities.md`.

## Review focus

These are the five inputs most likely to break Phase 1 that ordinary task tests would not touch. Each has a pinning test, added to the task named.

1. **A new account's first save.** D1 makes the row with `body` NULL (`server/accounts/characters.ts` `claim`), the room plays `Character::starting()`, and the first save is the first JSON. The serde default for a missing `story` is "past the prologue". If `starting()` or `to_json` loses `prologue: false`, every new character skips the gate after its first save. Pinned by `a_new_character_is_kept_short_of_the_prologue_and_one_kept_before_the_story_past_it` (Task 4).
2. **The reset boundary from a Thursday epoch.** An off-by-one in the 09:00 offset, or in the five days to the first Tuesday, shifts every day and week. Pinned by real dates in `a_day_turns_at_nine_utc` and `a_week_turns_on_tuesday_at_nine_utc` (Task 1): 2026-11-17 is a Tuesday, Unix minute 29,915,100.
3. **Two rooms whose clocks differ by seconds.** Under a turnover written as `!=`, a player who moves from a room just past 09:00 to one just before it would wipe a clear and could take it twice. Pinned by `a_day_never_turns_back_for_a_room_whose_clock_is_behind` (Task 4).
4. **The prologue's ask arriving before the kept character.** The token is claimed asynchronously, after the welcome. An ask answered on the unkept starting character is then overwritten by the restore. Pinned by `the room is told the prologue was played once for each word on the gear that says it is not kept` (Task 5) and `a_players_gear_says_whether_they_finished_the_prologue` (Task 5).
5. **A refusal after the welcome.** The gate can only judge the character once the token is claimed, so 4003 always comes after the welcome. A page that treats it as a dropped network rejoins forever. A page that does not travel leaves the player alone in a shut patrol. Pinned by `a room whose gate shuts is never joined again, and says why` (Task 6) and `a room whose gate shuts sends the player back to their ship, the veil saying why` (Task 7).

```rust
pub const RESET_MINUTE: u64 = 9 * 60;
/// Tuesday 6 January 1970 09:00 UTC: Unix day 0 was a Thursday, so the first Tuesday came five days on.
const FIRST_WEEK_MINUTE: u64 = 5 * DAY_MINUTES + RESET_MINUTE;
#[must_use] pub fn day_of(unix_minutes: u64) -> u64;              // resets passed since Unix time began
#[must_use] pub fn week_of(unix_minutes: u64) -> u64;             // Tuesday resets passed
#[must_use] pub fn minutes_to_next_day(unix_minutes: u64) -> u64; // 1..=DAY_MINUTES
#[must_use] pub fn minutes_to_next_week(unix_minutes: u64) -> u64;// 1..=WEEK_MINUTES
```
`day_of(m) = (m + DAY_MINUTES - RESET_MINUTE) / DAY_MINUTES`. `week_of(m) = (m + WEEK_MINUTES - FIRST_WEEK_MINUTE) / WEEK_MINUTES`. Each countdown is the period less the remainder of the same shifted value.

## What I could not determine, and how I chose

2. **The record's shape.** `today { day, cleared: set of tiers, bounties: place → count }` and `this_week { week, elite, abyss, boon }`. The Abyss boon's week is the week the record holds. There is no "turned in" mark for bounties: Phase 5 adds what the board needs, under `serde(default)`.
